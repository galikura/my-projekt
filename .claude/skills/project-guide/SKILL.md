# Работа с my-projekt

Применяй цикл: **инвентаризация → задача → изменения → документация → проверки → отчёт**.
Сначала устанавливай факты, затем действуй. Не создавай приложение, сервер, CRM,
API, базу данных или инфраструктуру только потому, что они упомянуты в планах.

## 1. Проверь актуальное состояние

Исходный снимок на момент создания skill:

- это документационный GitHub-профиль, а не готовое приложение;
- основная информация находится в `README.md`, оформление — в `assets/banner.svg`;
- сервиса, интерфейса, API, базы данных и настроенного deployment нет;
- `package.json`, lockfile, scripts, тесты и CI отсутствуют;
- технологический стек в README — ориентир для будущих продуктов, а не список
  установленных зависимостей.

Этот снимок не заменяет проверку. При расхождении доверять нужно текущим файлам
и фактическому выводу команд, а устаревшее описание следует явно отметить.

Перед содержательным ответом или изменением:

1. Определи корень репозитория, посмотри актуальное дерево без `.git`,
   зависимостей и generated-каталогов.
2. Прочитай относящиеся к задаче разделы `README.md`.
3. Выполни `git status --short --branch`. Перед правками изучи также
   `git diff` и `git diff --cached`, чтобы не перезаписать существующую работу.
4. Проверь наличие и при наличии прочитай:
   - `package.json`, включая `scripts`, `packageManager`, `engines` и workspaces;
   - `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lock` или `bun.lockb`;
   - `.env.example`, `.gitignore`, тестовые и lint-конфигурации;
   - `.github/workflows/`, deploy-конфигурации и дополнительную документацию.
5. Не читай и не выводи значения реальных `.env`. Для анализа требований
   используй имена переменных из примеров и публичной документации.
6. Раздели сведения на **факт**, **план** и **неизвестно**. Наличие технологии
   в README не доказывает её использование.

Не устанавливай зависимости ради одной инвентаризации.

## 2. Объясни структуру

- Перечисли реально найденные файлы и каталоги с их назначением.
- Отдельно укажи, что подтверждено файлами, что является планом и что не проверялось.
- Если приложения по-прежнему нет, прямо скажи, что запускать сервис не требуется.
- `git clone` и `cd my-projekt` описывай только как получение копии репозитория,
  а не как запуск.
- Для локального просмотра предлагай README на GitHub или в Markdown-preview,
  а `assets/banner.svg` — в браузере или графическом редакторе.
- Если приложение появилось, описывай его по исходникам, манифестам и scripts.

## 3. Запусти сервис по фактическим командам

Если исполняемого проекта нет:

- сообщи, что подтверждённого способа запуска нет;
- не выполняй `npm install`, `npm run dev`, `build`, `test` или `lint`;
- не инициализируй приложение и не устанавливай зависимости;
- предложи только просмотр существующих README и SVG.

Если приложение появилось:

1. Прочитай реальные `scripts` и сопоставь их с README. Для monorepo сначала
   определи нужный workspace и рабочую директорию.
2. Выбери package manager по согласованным `packageManager` и lockfile. Если
   доступен только один признак, используй его. При конфликте lockfile или
   отсутствии признаков уточни выбор, не выбирая npm молча.
3. Используй существующий script, соответствующий запросу. Не предполагай,
   что обязательно есть `dev`, `start`, `build`, `test` или `lint`.
4. Проверь обязательные переменные по `.env.example` и документации; не
   придумывай значения и не раскрывай секреты.
5. Не обновляй зависимости и не переписывай lockfile ради запуска без причины.
6. Запусти подтверждённую команду. Зафиксируй команду, рабочую директорию,
   состояние процесса и фактический URL/порт из конфигурации или вывода.
7. Не называй сервис запущенным, пока это не подтверждено. Не предполагай
   типовые порты вроде `3000` или `5173`.
8. При ошибке приведи точное сообщение и выполненную команду. Исправляй только
   относящуюся к ошибке причину, затем повтори исходную команду.
9. Останови запущенный для проверки фоновый процесс, если пользователь не
   просил оставить его работающим.

## 4. Вноси минимальные изменения

1. Сформулируй объём работ и прочитай только связанные файлы.
2. Сохрани существующие незакоммиченные изменения и ограничь diff задачей.
3. Сохраняй русский язык документации, стиль Markdown/HTML, UTF-8, текущие
   line endings, отступы, относительные ссылки и осмысленные `alt`.
4. Не переписывай файл целиком ради локальной правки. Не делай общий
   рефакторинг, переформатирование или замену SVG без необходимости.
5. Не меняй зависимости, конфигурацию, контакты и позиционирование без запроса.
6. Учитывай регистр имён: Windows может его игнорировать, а GitHub — нет.
7. После правки просмотри diff, staged-изменения и untracked-файлы.

## 5. Синхронизируй README

Обновляй `README.md` по прямому запросу либо когда изменились документируемые
сведения: структура, назначение, требования, установка, запуск, команды, env,
проверки, публикация, возможности, ограничения или дорожная карта.

- Изменение только внутренней конфигурации `.claude` само по себе не требует
  обновления README.
- Меняй только устаревшие или затронутые разделы, сохраняя остальной текст.
- Не переноси планируемые технологии в список установленных.
- Не выдумывай команды, порты, env, демо-URL, тесты, CI или deployment.
- Различай «script определён» и «команда успешно выполнена».
- После появления приложения скорректируй утверждения об отсутствии сервиса,
  структуру и инструкции запуска по подтверждённым данным.
- Если обновление не требуется, кратко укажи это в итоговом отчёте.

## 6. Проверь ошибки и результат

Для любого изменения:

- выполни `git diff --check`; при staged-изменениях также `git diff --cached --check`;
- просмотри `git diff`, `git diff --cached` и `git status --short`;
- отдельно прочитай новые untracked-файлы: обычный `git diff` их не показывает;
- запусти относящиеся к изменениям tests, lint, typecheck и build только если
  соответствующие scripts или конфиги действительно существуют;
- при наличии CI сверь локальные проверки с workflow;
- не устанавливай отдельный toolchain только для документационной правки.

Для изменённого Markdown:

- проверь локальные Markdown-ссылки и изображения, а также HTML `src`/`href`;
- разрешай относительные пути от каталога документа;
- отбрасывай query/fragment перед проверкой файла и проверяй точный регистр пути;
- для fragment-only ссылок подтверди наличие соответствующего заголовка;
- не считай ссылки внутри code fences навигационными;
- не проверяй `https:`, `mailto:` и `tel:` как локальные пути;
- не объявляй внешние ссылки проверенными без фактического сетевого запроса.

При изменении `assets/banner.svg` или ссылки на него проверь фактический рендер:
текст, русские символы, градиенты, обрезку, пропорции и элементы `title`/`desc`.
Если визуальный просмотр недоступен, отметь его как пропущенный: чтение XML не
заменяет визуальную проверку.

Каждой проверке дай честный статус:

- **PASS** — действительно выполнена успешно;
- **FAIL** — приведи точную ошибку;
- **NOT RUN** — укажи причину;
- **NOT APPLICABLE** — объясни, почему проверка не относится к изменению.

Отсутствие тестов не называй успешным тестированием.

## 7. Подготовь к публикации

При запросе «подготовь к публикации»:

1. Выполни `git status --short --branch` и проверь ветку, upstream и remote.
2. Просмотри staged/unstaged diff и список untracked-файлов.
3. Убедись, что входят только предназначенные файлы и нет секретов, реальных
   `.env`, ключей, случайных или generated-файлов.
4. Подтверди, что README актуален, либо объясни, почему обновление не нужно.
5. Выполни применимые проверки и перечисли результаты, ошибки и пропуски.
6. Укажи блокеры и оставшиеся риски. При необходимости предложи сообщение коммита.
7. Остановись: подготовка не означает разрешение на commit или push.

Разрешения не наследуются между действиями:

- **commit** — только после явного запроса; добавляй названные файлы, просмотри
  staged diff, после коммита сообщи hash и оставшиеся изменения;
- **push** — только после явного запроса; проверь фактические remote, ветку и
  upstream, затем сообщи remote, ветку и commit;
- **PR, release и deploy** — только после отдельного подтверждения и по реально
  существующей конфигурации или документации;
- не используй force push, не меняй ветку и не выполняй merge без запроса.

Без фактической отправки пиши «готово к публикации», а не «опубликовано».

## 8. Дай итоговый отчёт

Используй компактную структуру:

1. **Состояние проекта:** факты отдельно от планов, если это важно для задачи.
2. **Изменено:** файлы и суть правок.
3. **README:** обновлён / не требуется / не обновлялся по запросу.
4. **Проверки:** команды и ручные проверки со статусами.
5. **Осталось:** ошибки, ограничения и необходимые действия пользователя.
6. **Публикация:** готовность и фактически выполненные Git-действия.

При появлении приложения обновляй исходный снимок этого skill только в рамках
задачи по сопровождению skill; во время остальных задач используй актуальные
файлы и сообщай о расхождении, не изменяя инструкции попутно.
